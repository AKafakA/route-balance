## A1. Response to Reviewer 287j (29 Jul 2026, modified 30 Jul)
Related work clarify LLM-D and AIBrix provide serving infrastructure with routing and load-balancing only. RouteBalance (RB) focuses on a different policy boundary to join quality, latency, and cost when assigning each request to a concrete instance in heterogeneous deployment.
Q1: Batching versus continuous batching. There are two independent scheduling layers.
- Global assignment in RB. RB selects the serving instance for each incoming request.
- Engine-level continuous batching. After dispatch, each vLLM instance retains its normal continuous-batching loop and groups assigned requests into accelerator execution batches.
Thus, RB does not replace vLLM continuous batching. Once dispatched, a request immediately enters the selected instance's normal engine-level scheduling loop.
RB additionally forms scheduler-level scheduling rounds. Incoming requests first enter a global queue, and the next (B) requests, where (B) is chosen adaptively, are assigned together. Before each round, RB starts from the latest instance telemetry. It then predicts per-request quality and output length with the KNN estimator and predicts TPOT for each candidate instance with the XGBoost heads.
There is no mandatory minimum batch size. A scheduling round fires when either the adaptive size limit is reached or the timeout expires. Therefore, a lone request waits at most the timeout, and all formation delay is included in the reported client-observed end-to-end latency.
The rationale is threefold:
- After each assignment, RB immediately updates its local dead-reckoned view of the selected instance, so later requests in the same round do not repeatedly observe the same stale pre-dispatch state.
- Prediction cost is amortized across the round because request embeddings and candidate scoring can be computed in parallel. Measured decision compute falls from 44.7 ms at [λ=6] to 25.7 ms at [λ=24].
- Quality, cost, and latency are normalized over the candidates in the same round before weighted scoring, making the combined objective comparable across heterogeneous tiers.
Q2: Adaptive batch size. The current policy uses the fraction of instances with at least one waiting request: ratio (<0.3): batch size 4, timeout 50 ms; ratio (<0.7): batch size 16, timeout 100 ms; otherwise: batch size 32, timeout 200 ms. ... Disabling adaptivity increases end-to-end latency by 5–7% as measured in paper. With batch size 1, RB falls back to serial estimation and loses the amortization benefit of scheduler-level batching.
Q3: KV cache, prefix caching, and TTFT. The submitted objective is decode-dominated: predicted per-(model, GPU) TPOT multiplied by queue-aware decode iterations. TTFT and KV occupancy are not separate objective terms, although KV utilization and free-block count are features of the TPOT predictor. Model choice affects KV pressure through model size and sequence length. The submitted evaluation uses single-turn prompts and automatic prefix caching was enabled in vllm by default without overriding by us. Explicit TTFT/prefill and prefix-affinity terms are future work.
Q4: revision commitments: redraw Figure 1; remove/mark RoBERTa; request-flow walkthrough + seven workload sources in appendix; move Table 2 next to Eq 1–2; replace radar chart; LPT pseudocode; baseline appendix table (training, routing policy, dispatcher, state access, batching/concurrency mode, tuned parameters); define dead reckoning: "starting from the latest asynchronous telemetry, the scheduler locally applies each assignment's predicted queue effect and reconciles the estimate when the next authoritative update arrives."

## A2. Response to Reviewer gTfM (29 Jul 2026, modified 31 Jul)
Q1. We built exactly the alternative you propose: the same objective and the same within-tier queue tiebreak, with the learned head's queue-conditioned estimate replaced by a fixed per-tier TPOT constant. The constants are per-tier medians across the whole sweep rather than at one operating point — 3B 10.7, 7B 19.9, 14B 16.5, 72B 42.6 ms/token, verified against measured inter-token latency at 0.22 ms/token mean absolute error. Both arms use RB's (0.5, 0.3, 0.2) weights and differ only in the TPOT estimator. [table λ12/λ24] ... The two arms are equivalent.
Latency prediction clarification. Each XGBoost head predicts TPOT only, with one head per (model, GPU) tier trained from a tier-local QPS sweep. Its inputs are the tier's serving-state signals and the request's predicted output length; it does not consume request text. End-to-end latency is then computed analytically as predicted TPOT multiplied by the request's estimated decode iterations: pending decode tokens divided by the current decode batch size, plus the request's own KNN-predicted output length.
Q2. TTFT is not an explicit term, as our target is decode-dominated generation. Prefix affinity is likewise not modeled: our corpus is single-turn, so cross-request reuse is minimal and the setting is uniform across compared systems. KV occupancy is not a term either, but KV utilization and free-block count are features the TPOT head consumes, reaching the assignment through predicted TPOT.
Q3. Yes, centralized by design: one assignment decision per request over a global dead-reckoned view ... decision compute per request falls 44.7 → 25.7 ms from λ=6 to λ=24, as one prediction round amortizes over a batch.
Q4. Yes, fixed per run — RB is an online assignment layer over a given deployment, not an autoscaler. It does respond to a changed deployment without retraining: in the topology experiment ... we re-provisioned the small-model pool and re-ran every system with nothing retrained.
