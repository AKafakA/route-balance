## (c) Claims in the draft text that the sources contradict or cannot confirm

Draft under test: "Production balancers never fetch engine stats per request: they read a periodically scraped metrics cache
(llm-d endpoint picker, AIBrix) or local in-flight counts (Envoy/NGINX least-request, LiteLLM least-busy); Envoy's LEAST_REQUEST
uses power-of-two choices over active requests by default; SGLang's router and Dynamo's KV router combine cache affinity with load;
LiteLLM offers latency-based routing from observed latencies; vLLM Semantic Router picks a model from a prompt classifier and is not
load-aware; TEI serves embedding models with dynamic batching."

1. **"never fetch engine stats per request"**: this cannot be confirmed as a universal claim. What the sources support is narrower:
   none of the eight routers inspected fetches engine load statistics on the request path. Two qualifications:
   - AIBrix `least-request` does make a **synchronous per-request read**, but of gateway-maintained running-request counters in
     Redis (100 ms timeout, falling back to the local atomic counter), not of engine stats. LiteLLM `least-busy` also reads Redis
     per request when Redis is configured.
   - The llm-d EPP may call vLLM's `/render` per request for tokenization when a `token-producer` with that backend is configured.
     This is a tokenizer call, not a load statistic.
   Suggested wording: "the balancers we inspected do not query engine load on the request path".
2. **"periodically scraped metrics cache (llm-d endpoint picker, AIBrix)"**: confirmed for engine metrics (llm-d 50 ms, AIBrix
   1 s defaults), with one gap. AIBrix's `least-request` and `power-of-two` use **gateway-side in-flight counts**, not the scraped
   cache, and llm-d also offers an optional EPP-local `inflight-load-producer`. Both systems therefore combine the two mechanisms.
   Listing AIBrix under "scraped cache" alone is incomplete.
3. **"local in-flight counts (Envoy/NGINX least-request, LiteLLM least-busy)"**: confirmed. Qualifications: NGINX's directive is
   `least_conn`, which counts active *connections*; counts are shared across NGINX worker processes only when a `zone` is
   configured; LiteLLM's counts are mirrored to Redis when Redis is configured.
4. **"Envoy's LEAST_REQUEST uses power-of-two choices over active requests by default"**: confirmed only **when all host weights
   are equal**. With unequal weights Envoy switches to weighted round-robin with `weight/(active+1)^bias`. Add "for equally
   weighted hosts".
5. **"SGLang's router and Dynamo's KV router combine cache affinity with load"**: confirmed. Precision: SGLang `cache_aware`
   *switches* between prefix affinity and shortest-queue when load is imbalanced (thresholds 64 absolute / 1.5x relative). It
   does not blend them. Its load signal is the router's own in-flight count, and its cache signal is an approximate tree of
   past routing decisions (no engine query). The docs line "Load Monitor feeds cache-aware and power-of-two policies" is **not
   borne out by the code at this SHA**: the monitor updates only `power_of_two` policies. Dynamo blends overlap credit and
   predicted load in one cost function, and its cache state is pushed by workers as KV events.
6. **"LiteLLM offers latency-based routing from observed latencies"**: confirmed. For any follow-on wording: latency is the mean
   of the last 10 observed samples (a sliding window, not an EWMA), normalised per completion token when usage is reported,
   TTFT for streaming. Failures from timeouts add a 1000 s sample.
7. **"vLLM Semantic Router picks a model from a prompt classifier and is not load-aware"**: **partly contradicted**.
   - Supported: it chooses a model or model pool and explicitly leaves replica selection to an inference router. The default
     selection method is `static`, and nothing reads engine or replica load.
   - Contradicted: it ships optional selectors that use runtime state. `multi_factor` has a load term (router-local in-flight
     requests per model, which its own code calls "load-aware selection"). `latency_aware` uses router-observed TPOT/TTFT
     percentiles.
   - Imprecise: decisions come from multiple "signals" (classifiers, embeddings, keywords, etc.), not a single prompt classifier.
   Suggested wording: "selects a model from request signals and, by default, does not consider replica or engine load; replica
   choice is delegated to an inference router."
8. **"TEI serves embedding models with dynamic batching"**: confirmed ("token-based dynamic batching"). TEI also serves
   sequence-classification and re-ranker models, which is useful context for hosting a classifier-style model router.
9. **Context not in the draft (RouteLLM)**: the RouteLLM server scores each request synchronously inside its async handler, one
   prompt at a time, with no batching. If the paper says anything about how model routers are hosted, RouteLLM is an example of
   inline per-request scoring. The repository was last updated in August 2024.
10. **Naming**: the reference endpoint picker now lives in `llm-d/llm-d-router`. The GIE repository keeps only a lightweight EPP
    and the API. Cite GIE v1.5.0 (`df9f890`) or llm-d-router (`c46a1b9`) for EPP code.
