## Lessons Learned (March 27)

### 1. Never trust "fused" means fused
The word "fused" in directory names meant nothing — 4 separate models trained in a loop. **Always verify architecture claims by reading the training code, not the directory name.**

### 2. Paper formulation diverges from implementation silently
The MILP formulation had cost-based budget (`C_{r,i} ≤ budget`), memory capacity constraints, and makespan terms. The code had none of these. Nobody noticed because the paper was written independently of the code. **Every equation in the paper must have a corresponding code path, verified line-by-line.**

### 3. Mislabeled functions are worse than missing functions
`predict_ttft()` returning E2E latency caused double-counting that inflated all latency scores. The function name was wrong but it "worked" (returned a number). **Always check what a function actually computes, not what it's named.**

### 4. Static fallbacks mask missing implementations
`predict_tpot()` returned a static lookup, hiding that no TPOT model was ever trained. The scheduler worked fine with static values — just sub-optimally. **Log warnings when fallbacks are used, don't silently degrade.**

### 5. Normalization scope matters more than normalization method
Per-request normalization made latency=1.0 and latency=1.1 look equally "bad" after normalization. Batch-wide normalization is needed for consistent scale. **Document normalization scope as a design decision, not an implementation detail.**

### 6. Balance score proxy ≠ actual metric
Queue depth was used as a proxy for GPU memory utilization. With different model sizes using 7× different KV cache per token (3B: 55KB vs 14B: 393KB), queue depth is a terrible proxy. **Always use the actual metric when available.**

### 7. Test with assertions, not just "it runs"
The smoke test showed "200ms overhead, 140 tokens output, no errors" — but didn't verify that the budget filter actually rejected expensive instances, that normalization used batch-wide context, or that the balance score reflected GPU memory. **Add assertion-based health checks, not just "does it crash?"**

## Critical Bugs Found & Fixed

### 0. Latency Predictor Double-Counting (FIXED)
- `predict_ttft()` returned E2E from E2E XGBoost. Scheduler computed `e2e = "ttft" + E[length] × tpot` = double-count.
- **Fix**: Trained separate TTFT + TPOT XGBoost on GPU VM. Fixed sidecar to load 3 models. predict_ttft→TTFT model, predict_tpot→TPOT model, predict_e2e→E2E model.
- Training feature: `actual_output_tokens` (via `--use-actual-output-len`), mapped to `num_predicted_output_tokens` at serving time. XGBoost auto-drops for TTFT/TPOT (~0 importance confirmed).

### 1. "Fused" Models Were Per-Model (FIXED)
- All "fused" ModernBERT were 4 separate encoders. Created true `MultiHeadEncoder`.
- Results: Fused matches/beats per-model (48.2% vs 47.3% on 14B bucket).

### 2. Budget Filter Token-Based, Not Cost-Based (FIXED)
- Paper: `C_{r,i} ≤ RSO_budget(r)` (monetary). Code: `P(tokens ≤ B)` (model-independent).
- **Fix**: Added `budget_cost` field. Filter converts cost→per-model token budget via `cost_per_token`.

### 3. Balance Score Used Queue Depth, Not GPU Memory (FIXED)
- Now uses `kv_cache_utilization` + projected memory gain: `projected = current + (prompt + E[output]) × kv_bytes_per_token / capacity`.
- Config: `model_kv_config` with per-model KV bytes (3B:55KB, 7B:115KB, 14B:393KB, 72B:328KB).

### 4. Normalization Was Per-Request, Should Be Two-Phase (FIXED)
- Phase 1: Batch-wide min/max for quality+cost (from ModelEstimator, pre-loop).
- Phase 2: Stats-initialized accumulated min/max for latency+balance (running, expand-only).

### 5. No Global SLO Enforcement (FIXED)
- Added `global_slo` config. Filter checks `min(request.slo, global.slo)`.
- Separate counters: `filtered_ttft_global`, `filtered_tpot_global`.
