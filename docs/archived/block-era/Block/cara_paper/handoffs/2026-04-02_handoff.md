## vLLM Semantic Router Study (COMPLETED)
- Repo cloned: `~/Code/llm/semantic-router/`
- Papers: arXiv 2603.04444 (signal-driven routing), 2603.21354 (vision paper)
- RouterArena (arXiv 2510.00202): standardized LLM router evaluation platform

### Key Findings
- SR routes to MODELS, Cara fuses model selection + load balancing jointly — different layer
- SR: N separate LoRA forward passes (1 per task, parallel goroutines) vs Cara: 1 fused multi-head forward pass
- SR supports CPU mode (`use_cpu: true`) — standard for evaluation (RouterArena)
- SR has no batch scheduling, no SLO filtering, no budget compliance, no load balancing

### Overhead Profiling (This Session)
| Component | CPU (EPYC) | GPU (L40S) |
|-----------|-----------|------------|
| Tokenization | 0.06ms | 0.06ms |
| Encoder forward | 55ms | 3.2ms |
| Total estimate() | ~60ms | ~3.3ms |

**Rust vs Python**: only saves ~1-5ms (Python dispatch). GPU kernel dominates — same in any language.

### Decisions Made
- **Main eval**: all 18 nodes serving, CPU scheduler co-located (standard approach, same as RouterArena)
- **Overhead reduction**: ONNX export (55ms → ~15ms on CPU) — biggest practical win
- **No dedicated GPU scheduler**: GPU memory should serve KV cache, not run router
- **Benchmark script**: `benchmark_estimator_overhead.py` with `--compare` for CPU vs GPU reproducibility
- **SR baseline**: deploy SR + Round Robin on CloudLab as baseline (Envoy + extproc binary)

### Paper Positioning
Cara = joint model-selection + load-balancing (fused). SR = model-selection only (no LB).
Report CPU overhead in main results, GPU numbers in appendix table.
