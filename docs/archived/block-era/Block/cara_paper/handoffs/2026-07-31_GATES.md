# v3 gates — what each one proves, and what it does not

> 📕 **Operating the window: `2026-08-02_S2_RUNBOOK.md`.** This file is the *why* behind each
> gate; the runbook is the ordered *what to type*.

**Purpose of this document: to be attacked.** Every gate below is stated with the defect it
exists to catch, the evidence it reads, how it has been tested, and — explicitly — what it
still cannot prove. A gate whose limits are undocumented is the thing that produced this
project's worst failures.

**The governing rule, learned the hard way:** *a gate must read the effect, never the
declaration, and must never derive its expectation from the same artifact that produced the
thing being checked.* Both halves have been violated in this repo within the last week:

- The static-TPOT check compared an env var against an echo of the same env var.
- The Gemma fleet gate read one config schema, saw 8 of 14 backends, compared 8 against its
  own partial view, and printed `8/8 GATE PASSED`.
- `RULE-0` hashes a manifest that is **empty**, so it passes against any tree.

## AUTHOR-APPROVED 2026-08-02 — three burst decisions implemented, plus a fleet monitor

### G-PAIRING · `verify_pairing.py` — pre-registered choice 3, finally verified

Choice 3 says the same `--seed` must give both arms identical arrivals, "verified
empirically ... if it does not hold, the pairing argument evaporates silently". Nothing
verified it.

**Post-hoc cell comparison is impossible AND weaker:** `response_details` carries no arrival
timestamp, and two live cells differ by jitter, so you would compare realised send times
rather than the arrival PROCESS. Instead this **AST-lifts `get_request` and
`_get_current_request_rate` verbatim from the shipping file and execs them** — real code, not
a re-implementation that could drift — with `asyncio.sleep` recorded and `time.time` frozen
(a live clock made the digest irreproducible, which would have reported jitter as a pairing
failure).

Verified: determinism · both arms identical · a different seed differs · gamma-0.25 burstier
than Poisson. **The CVs match theory independently: Poisson 0.971 vs 1.0, gamma-0.25 1.976 vs
1/√0.25 = 2.0.** ~0.23 s per schedule, so the full 72-combination preflight costs ~17 s.

### G-SEEDSCOPE · the seed must vary arrivals and NOTHING else

`benchmark_serving` seeds **both** RNGs from one `--seed` (:1648-1649). Only numpy drives
arrivals; the **python** stream feeds `_sample_rso` (per-request TTFT/TPOT SLOs, budget_cost,
quality_min) and the LoRA picker. If either were on, the same seed varying arrivals would
also vary those — and burst-vs-Poisson differences would be partly attributable to them.

**Today it is safe and now gated:** `--rso-rate` defaults to **0.0** so `_sample_rso` returns
before its first `random.random()`, and no runner passes `--rso-*` or `--lora-modules`. The
gate enumerates every RNG consumer, asserts each sits behind an off-by-default flag, re-checks
the default, and scans the runners. Proven to fail on a runner that enables RSO, and on a
missing runner.

### G-MONITOR · `orphan_monitor.py` — periodic, detect-only

> ⚠ **A fail-closed gate needs a supervised watcher, or it becomes a single point of failure
> with the OPPOSITE sign (fixed 2026-08-02).** The per-cell check refuses when the status is
> missing or stale — correct — but **nothing restarted the monitor**. A monitor dying at hour 6
> of a 27 h grid would have stalled every remaining cell, unattended, and burned the window: a
> device added to protect the run would have been the thing that ended it.
>
> `ensure_monitor()` now runs **between rates and before Q1** — never mid-cell, so a restart
> cannot perturb live work. It checks two things, because they are not the same: the process is
> alive, **and** the file the cells actually gate on is fresh on the head node. Alive-but-not-
> reporting also triggers a restart. Three attempts, then `die` with the `MONITOR_OPTIONAL=1`
> escape spelled out — the driver stops rather than running blind.
>
> **Verified against the real fleet:** with no monitor running, `ensure_monitor` reported
> `NOT RUNNING — restarting`, restarted on attempt 1, and the head node's published status was
> **3 s old with 0 findings**. The freshness probe was tested in all three states on the head
> node (fresh → rc=0, backdated → rc=1, missing → rc=1) because its quoting survives two levels
> of shell and could not be trusted by reading. Four self-test cases, including
> **unrestartable → the driver STOPS**.

> 🔴 **The first version was INERT, and the fix is the point.** The monitor runs on the **VPS**;
> the runners run on the **cluster head node**. It wrote the flag to a VPS path and exported
> that same path to the runners, so `[ -f "$flag" ]` on the head node was false forever and the
> gate **silently never fired** — writer and reader disagreeing about where the evidence lives,
> this campaign's most repeated defect, freshly reintroduced *inside a gate written to catch
> contamination*.
>
> Three changes, each verified by execution:
> 1. **Publish where the reader lives.** The monitor ships its status to
>    `head:~/S2_CONTAM_STATUS` every sweep (atomic `.tmp` + `mv`), and the driver **proves the
>    first heartbeat arrived** before proceeding — "the process started" is not "the reader can
>    see it", and that assumption is exactly what made the first version inert.
> 2. **A HEARTBEAT every sweep, not only on contamination.** Absence of a flag cannot mean
>    "clear", or a dead monitor is indistinguishable from a clean fleet — the same fail-open
>    hole one level up. The reader refuses on a missing or **stale** (>2100 s) status;
>    `MONITOR_OPTIONAL=1` is the explicit, deliberate opt-out.
> 3. **`ssh -n` had to go for the publish call.** Every other ssh here uses `-n` to protect the
>    loop's stdin, but `-n` redirects stdin from `/dev/null` — so the piped JSON never reached
>    `cat` and the file published **empty**. The exit code was 0. Caught only by reading the
>    file back from the head node rather than trusting rc.
>
> **Verified end-to-end on the live head node:** sweep → publish → read back
> (`{"ts": ..., "n_findings": 0, "findings": []}`) → reader returns *cell proceeds*. Reader
> proven in five states: clean+fresh · findings · stale heartbeat · no file · explicit opt-out.

The orphan gate runs **once**, pre-flight; the contamination it exists to catch happened
**during** a run (six orphaned `p1_pareto.sh`, oldest 2 h 48 m old, 5.7× latency inflation
while every cell still PASSED RULE-0).

**A naive orphan check is wrong here** — during a live cell one `benchmark_serving` and one
`cara_serve` are expected, so the pre-flight predicate would fire on every sweep. The real
signature is **duplicates · stale · misplaced**.

* **It never kills.** A wrong kill costs more than a late report; the decision stays with the
  author.
* **Runners read a local FLAG between cells** — zero cluster traffic at that moment — and
  refuse the NEXT cell. A cell in flight is never aborted.
* Ran against the live lease: **0 findings**, correctly counting `sched: 1` on the head
  without flagging it. All six classification branches proven by unit case.

### Burst fleet is a declared decision, not a default

`BURST_FLEET` must be `2tier`|`4tier` and must agree with `ALLOWED_HW`. The block costs ~4 h
against a window already holding 30.4 h of committed work; the script refuses to guess.

### Statistics: t, and a paired test

`burst_analysis.py` used **z = 1.96 on n = 6**. Correct is **t(0.975,5) = 2.571**, 31% wider,
and the verdict is a separation test. Now uses a t table, and reports a **paired** test on
per-seed differences — correct because the arms share a seed (now *verified*, above), and
strictly more powerful. Independent CIs still print for reference. Recovers the injected truth:
learned 1.359 (1.35), static 1.596 (1.60), paired t(5) = −28.65, all seeds same sign.

## G-FILL · a tuned point must not read as a swept one (new 2026-08-02)

**Catches:** the integrity failure that RB retuning would otherwise create.

The author approved running extra RB tuples after the grid, to close a dominance deficit
(plan Phase E′ rule 4). `dominance.py` identified rows by **filename alone** and read only
`cap` from metadata — so a tuple tuned *after seeing the frontier* appeared in the table
indistinguishable from a pre-registered grid member. The plan's honesty guard ("MUST BE
LABELLED as an interpolated point") was a **print statement, not a mechanism**.

Now: cells carry a `fill` stamp, and the verdict is computed **twice** — pre-registered tuples
only, and all tuples. If domination depends on an interpolated tuple it says so:

```
[fill] 1 interpolated tuple(s) present: ['(0.05,0.475,0.475)']
⚠ DOMINATION DEPENDS ON AN INTERPOLATED TUPLE. No pre-registered tuple dominates
  Dispatcher-only; ['(0.05,0.475,0.475)'] does. Any table MUST say so.
```

**Why this is legitimate at all:** the grid already sweeps each baseline's own knob (BR 4
thresholds × 3 dispatchers, AP 5 pw × 3), so densifying RB's simplex is symmetric, not
favouritism — *provided* which points were pre-registered stays visible. Three self-test cases.

⚠ **Still a protocol matter, not a code matter:** the suggestion rule is deterministic, but
*when to stop* is not. Adding fill points only where RB loses, and stopping once it wins, is
optional stopping. The defensible protocol is to apply the same ≤3-tuple rule at **every**
not-dominated rate and report **every** fill point run, including ones that did not help.

## G-PRESET · preset is identity, not decoration (new 2026-08-02)

**Catches:** two different systems averaged into one number.

Q1 now runs **two** RB presets — 532 (the posted configuration) and uniform (the robustness
case). `burst_analysis.py` paired by `(λ, seed)`, so two presets in one directory would have
been **pooled into a single degradation ratio**, reporting the mean of two systems as if it
were one.

Preset is now part of the identity end to end: cell **filename** (`qb_..._p<preset>_...`),
cell **metadata**, the **pairing key**, `per_lam`, and the paired test. Verified on a synthetic
set where 532 gives learned 1.30 vs static 1.62 and uniform gives 1.45 vs 1.46: it recovers
**both independently** — 532 significant at t(5) = −24.39, uniform not significant — which is
exactly the contrast pooling would have destroyed. An unknown preset is **refused**, not
defaulted. Seven self-test cases.

not work.** It said the evidence was `tpot_log.jsonl`. **Nothing in any tree writes that
file**, so the gate would have passed vacuously. It now reads the **decision log**
(`cara_serve --decision-log`, always on), which records the latency that actually entered the

**And the assertion was wrong too.** The old version asserted "one distinct TPOT per tier",
which **would have failed a correct static arm**: the learned XGBoost TPOT head runs in
*both* arms (it feeds `pred["e2e_latency"]`), so TPOT is queue-varying either way. The arms
differ only at `_lat_val` in the scorer:

```
learned : lat_s = pred["e2e_latency"]                       (queue-conditioned)
static  : lat_s = const[tier] * pred["expected_length"]
```

`expected_length` varies per request, so `lat_s` alone is not constant even under a correct
static arm. **The invariant is the RATIO.**

**Assertions, when the static prior is ENABLED (`--expect-static`):**

| | assertion |
|---|---|
| A | within a tier, `lat_s / expected_length` takes exactly **one** value |
| B | across tiers, those values must **differ** — a single global constant passes A while destroying the experiment |

## G-DRIVER · `v3_scripts/s2_driver.sh` — the phase gate, and how it failed

Added 2026-07-31 after the end-to-end rehearsal found the driver violating its own Rule 1.

**Rule 1 says: a failed phase STOPS the driver.** It did not. Three phases counted verified hosts
with `okc=$(grep -c PATTERN log 2>/dev/null || echo 0)`. `grep -c` **exits 1 when the count is

unreachable**. A guard that evaporates during argument expansion is invisible to every test that
only checks the passing path.

**Fix:** one `require_count` helper, both operands forced to single integers before any arithmetic
can reach a `die` argument, with an explicit non-numeric guard.

**Tested on fixtures:**

## G-ARMLEAK · the defect that motivated `GET /v1/config`

Found 2026-08-01 by running the FULL Q1 rather than the pilot alone.

`/v1/config` applies `slo_defaults.update(...)` — a dict **merge**. An arm-defining key
therefore survives until something overwrites it. `s2_q1.sh` alternates arms inside one
scheduler session, so every "learned" cell after the first static one silently inherited
the static prior.

**Measured, not inferred:**

| comparison | agreement |
|---|---|
| learned vs static | 3387/3534 = 95.84% |
| learned vs CONTROL (learned payload, posted after a static cell) | 3387/3534 = 95.84% |
| **static vs CONTROL** | **3534/3534 = 100.00%** |

Two independent comparisons cannot coincidentally share a numerator. The decision log
during the control read `static_active = {True}`. The control was a static run wearing a
learned label.

**Why the pilot could not catch it.** The pilot runs one cell per arm at the start of the
sequence, and its learned cell ran *before* any static cell existed to leak from. A
fail-fast check that samples only the beginning of a sequence cannot see state that
accumulates through it. This is a real limitation of the pilot design and applies equally
to Monday's run.

**Fixes — defence in depth, without changing global merge semantics** (other runners rely
on config-file defaults persisting; that is an author decision, and it is open):

| fix | effect |
|---|---|
| `EFFECTIVE_CONFIG` re-emitted on every POST | Phase A required this and it was never implemented; its absence is what HID the leak |
| `GET /v1/config` added | only POST existed, so the only way to ask "is a prior active?" was to set one |
| learned payload sets `static_tpot_ms_per_tok: null` | omission inherits; only an explicit value replaces |
| pre-cell arm assertion in `run_q1_cell` | refuses to bank a cell whose RESOLVED prior contradicts its claimed arm |

**Proven end to end on a node:** post static → prior set; post learned-by-omission →
prior STILL set; post explicit null → cleared. Four `EFFECTIVE_CONFIG` emissions, one per
change.

## G-DETACH · the runner hang that would have eaten a window

Found 2026-08-01T02:25Z, after Q1 completed cleanly.

Q1 finished at 02:09 with **24 cells OK, 0 INVALID** — and the driver then sat for 15+
minutes and would never have started the grid.

```
bash s2_q1.sh   state: S   wchan: do_wait
  └─ python3 -m block.global_scheduler.cara.cara_serve
```

`restart_v3` launched the scheduler as `( … & )`, expecting the subshell to orphan it to
init. It did not: `ps --ppid` showed `cara_serve` as a **direct child** of the runner. When
the runner reached its last line, bash blocked in `do_wait` reaping a server that never
exits. Nothing failed, nothing logged, and the phase simply never completed — the worst
shape for an unattended 35 h window.

**Three attempts, and the two failures are the instructive part:**

| form | outcome |
|---|---|
| `( cmd & )` | still a direct child |
| `setsid cmd` | **still a direct child.** `setsid(1)` forks only when the caller is already a process-group leader; under a non-interactive shell it is not, so it called `setsid()` in place — new session, same parent |
| `setsid --fork cmd` | always forks; the intermediate exits; the scheduler is reparented to init |

**Verified by execution**, not by reasoning — and deliberately run fully detached writing to
a file, because the first verification attempt hung through its own blocking ssh and gave an
ambiguous answer:

```
scheduler pid=1298214  ppid=1  sid=1298214   -> DETACHED: reparented to init
runner elapsed: 6.26s                        -> exits promptly instead of never
```

**Class of defect: a phase that neither fails nor completes.** Every gate in this document
answers "is this cell right?"; none answers "did the phase finish at all?". The driver's
per-phase timeout is the missing guard, and `--status` plus the resumable state file are how
a stalled phase is now detected rather than waited on.

## G-BATCHPATH · is batched KNN actually applied?

Added 2026-08-01 at the author's request, and the answer before it was **not provable**.

`EFFECTIVE_CONFIG.batched_path` was `hasattr(model_estimator, "estimate_batch")` — a
**capability**, true whenever the object has the method, whether or not the branch ever ran.
Both call sites are `elif`, so a preceding branch takes precedence, and the per-request
fallback is exactly the one that skips `_estimator_prompt()` — the chat-skew defect
(locked-defaults §E). Identical shape to the static-TPOT arm: declared, plausibly bypassed,
invisible afterwards.

`cara_serve` now **counts** both branches — `_SCORE_BATCHED_CALLS`, `_SCORE_PERREQ_CALLS` —
exposed via `GET /v1/config` and echoed in `EFFECTIVE_CONFIG`.

**Verified by execution on a node:**

```
before any request : batched=0 perreq=0
after 8 completions: batched=8 perreq=0
```

**Gate:** snapshot before and after each cell; **`score_perreq_calls` must not move**, the
counters must be **readable**, and **`score_batched_calls` must advance**. If it
does, some batch took the un-unwrapped fallback and the cell is suspect.

**Why it matters beyond bookkeeping:** the Phase Q1-BURST decision to use λ30 rather than λ28
rests entirely on the batched path having removed the scheduler-overhead blow-up (λ24→λ30
overhead 245→1120 ms pre-fix vs 147→172 ms fixed). That argument is only as good as the
evidence that the batched path is live, which until now was a `hasattr`.

## G-BOOSTERS · a partial fleet gets its own booster set, not a relaxed check (new 2026-08-02)

The A30-only reload fails `P2B_ARTIFACTS`, and that is the gate working: the shipped set
declares four tiers, two typed `_v100`/`_a100`, which this lease does not have.

**The fix that does not work, and why it matters.** A flag that waves `P2B` through would let
all four tiers stage and load. The predictor then prints `tiers: [...]` including hardware that
is absent, and **G-TIERS refuses** — because a predictor tier loaded for hardware not in the
fleet is precisely the P100 zombie-tier shape (D3/D4) that cost this campaign a day. So the
flag does not remove a failure, it **relocates it onto the guard we least want to relax**.

**What is implemented instead.** `make_fleet_boosters.py` builds a booster set filtered to the
tiers the fleet actually serves:

* the subset is **derived from `model_deployment.json`**, never hand-typed, so it cannot drift
  from what is deployed;
* `.xgb` bytes are copied verbatim and **md5-verified** — a rehearsal exercises the same heads,
  only fewer of them;
* only `instance_types` is narrowed in the metadata;
* a `FLEET_SUBSET.json` provenance file travels with the artifact, so a cell produced against a
  subset is distinguishable from one produced against the full set months later;
* a **deployed model with no head is a hard failure** (exit 2), not a smaller set — that is the
  genuine error the check exists to catch.

The generated set is then judged by the **unmodified** `P2B` validator and the **unmodified**
G-TIERS gate. Generator and validator are separate implementations on purpose: a bug in one is
caught by the other rather than shared.

**Gated to rehearsal.** `TPOT_SUBSET=1` is refused unless `S2_MODE=rehearsal`. Automatic
narrowing ("the set does not match, so shrink it") is the silent-workaround shape this campaign
keeps paying for. A production run on a partial fleet is an author decision and must name its
booster set explicitly with `TPOT_SRC=...`, which puts the choice in the command line and the
log rather than in an inferred default.

**Production is unaffected, verified rather than assumed:**

| check | result |
|---|---|
| full 4-tier set + 4-model deployment + `a30,v100,a100` | `P2B` PASS, G-TIERS PASS |
| old vs new stage-copy form, real booster set | byte-identical trees, same md5 `cc97ef44…` |
| generated dir under `s2_cluster/logs/` vs tree manifest | manifest unchanged (it covers `block/**/*.py` only) |
| `TPOT_SUBSET` / `TPOT_SRC` unset | generation skipped; shipped set used |

One production-path edit was required and is the only behavioural change outside rehearsal: the
stage copy now writes `$STAGE/models/cara/latency/deploy_tpot/` explicitly instead of relying on
the source directory's basename, because the scheduler's default path is `deploy_tpot` and a
generated subset has a different name. Proven byte-identical for the full set above.

Self-test coverage: **7 cases**, 2 of them MUST-FAIL — full set on a partial fleet still
refused, generator refuses a headless deployed model, subset passes real `P2B` *and* real
G-TIERS, byte fidelity, and the rehearsal gate read from the driver text itself.

## 🔴 G-DOMINANCE · the provenance sidecars failed a COMPLETE grid (found + fixed 2026-08-02)

The first end-to-end Phase E′ run refused a grid that was in fact complete:

**Fix:** `*.provenance.json` is excluded from the cell sweep, and *only* that suffix. Any other

## G-CONTAM · the contamination gate fired for the first time on real traffic (2026-08-02)

During the smoke grid the fleet monitor reported
`DUPLICATE_RUNNER on d7525-10s10325: 2 runners, ages [27, 240]`, and the gate refused the next
four cells — `pt_rr`, `pt_sq`, `pt_rand`, `pt_po2` — killing nothing, which is the designed
behaviour ("Nothing has been killed — that decision is yours").

**The gate behaved correctly. The cause of the second runner is NOT established.** What is
known: the driver kills orphans before starting a rate; one `p1_pareto.sh` for the whole rate is
expected and matches the age-240 process; a second appeared ~4 minutes in; `p1_pareto.sh`
contains no subshell fork or backgrounding in its cell loop that would duplicate its argv; and
the monitor's pattern is bracketed (`[p]1_pareto.sh|…`) so it cannot self-match an ssh wrapper.
The processes were gone before they could be inspected.

**Diagnostic gap, and the reason it stayed unresolved:** the finding records only *counts and
ages* — `"2 runners, ages [27, 240]"` — not pids or command lines. Recording argv would have
settled this in seconds. That is a proposed change, not made: it alters the monitor's output
format and the author has not approved it.

**Operational consequence for the window:** if this recurs it costs cells, four at a time, and
it fires on the *next* cell rather than corrupting the current one. It is a refusal, so nothing
banked is suspect — the 4 cells simply did not run.

### G-CONTAM RESOLVED (2026-08-02 23:00Z): the "duplicate runner" was the runner's own benchmark subshell

**Root cause, with the full evidence chain.** `bench_v3` (`lib_serve_v3.sh:222`) launches the
benchmark inside `( cd "$V3TREE" && python3 -m …benchmark_serving … )`. When a subshell is not
the script's final command, bash keeps it as a real second process whose argv is a
**byte-identical copy of the runner's** — for the entire benchmark.

* **Reproduced on the head node itself** (bash 5.1.16): the faithful shape yields two
  `bash <script>` lines, parent-child, for the subshell's full duration. A VPS demo with the
  subshell as the *final* command optimizes it away, which is why the first local repro
  misleadingly showed one process.
* **Fits every measurement**: the one sweep that landed inside a cell saw `runner: 2, sched: 1,
  bench: 1`; age 240 = the real runner (launch chain collapses via `exec` into a single
  process — verified from the generated launcher); age 27 ≈ cell 7's benchmark window; every
  out-of-cell sweep clean.
* **Consequence had it shipped**: benchmarks occupy most of each cell's wall time, so in the
  17-hour production grid nearly every 300 s sweep would fire DUPLICATE_RUNNER and each firing
  refuses the next cell. The smoke's single in-cell sweep cost 4 cells; production would have
  bled cells all night.

**Fix — in the classifier, not the runner.** `bench_v3` is the benchmark launch path and was
not touched. The monitor now captures **ppid** and collapses a process whose direct parent is
another match with **identical argv** (a shell clone). Every dangerous shape stays refused,
pinned by MUST-FAIL self-tests:

| shape | verdict |
|---|---|
| runner + its same-argv child + its benchmark | **healthy** (the production-saving case) |
| two same-argv runners, unrelated parents (stale + relaunch, the 05:25 signature) | refused |
| a clone whose parent died (reparented to pid 1) | refused |
| two concurrent benchmarks, even as children of the same runner | refused |

The monitor was restarted with the fixed code (the driver's `ensure_monitor` deliberately
*reuses* a monitor whose heartbeat is fresh, so a stale-code monitor would otherwise have been
inherited by production). First sweep with the new 4-column parser confirmed sighted:
`sched: 1` on the head. The 22:24 flag file is archived at
`s2_cluster/retired/CONTAMINATED.false-positive-20260802T2224`, and the driver clears/recreates
the flag at P0_REACH regardless.

Self-test: **153 cases, 84 MUST-FAIL, 0 wrong.**

## 🚫 UNALLOWABLE BUGS — final author rulings (2026-08-03 ~19:20Z)

**#1 High-rate BR pipeline collapse.** At λ≥18 — exactly the paper's §265 saturation onset —
BR's serial scoring queue plus per-request stats fan-out storms the scheduler (99.5%
whole-tier blindness measured) and kills the process (`aiohttp … Bad file descriptor`).
**A scheduler must never die from a baseline's load shape.** Mitigation landed: blind-absorb
(config-gated) + random-on-blind + loud blindness counters; post-window hardening queued
(connector limits / batched pipeline stats).

**#2 Budget all-rejected pin.** Bare `min()` over tied per-instance costs sent EVERY
all-rejected request to the first instance of the cheapest tier. Fixed (spread among
tied-cheapest, loud). LIVE in the paper's budget experiments — affected fraction to be
quantified from those cells before CR.

**Ruled NOT a bug — SQ first-on-equal-depth tie**: kept deterministic-first (era-consistent
with every published sq cell; the minimum instance is itself dynamic). The random-tie change
was reverted at the author's ruling; the no-silent-fallback and random-on-blind orders stand.
